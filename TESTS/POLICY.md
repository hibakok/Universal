# TESTS. Политика тестирования

Паспорт файла: TESTS/POLICY.md | слой: все | роль: принципы тестов проекта.

## Принципы

1. **Секунда — предел.** Каждый тест выполняется за время, неотличимое
   от нуля на глаз. Долгие проверки разбиваются на быстрые шаги
   или помечаются как «приёмочные» и запускаются только при смене этапа.
2. **Глубина не приносится в жертву скорости.** Быстрота достигается
   изоляцией и точностью проверок, а не их сокращением.
3. **Тест = процедура + эталон.** Ожидаемый результат записан заранее
   в тест-плане; сравнение с эталоном — строгим (байт-в-байт).
4. **Пирамида:**
   - кирпич (карточка: вход -> выход) — проверяется в составе модуля;
   - модуль (тест-план вида T-M*-*) — основной уровень;
   - этап (DoD в ROADMAP) — приёмочные проверки.
5. **Детерминизм.** Один вход — один выход. Недетерминированное поведение
   запрещено (правило R8) и не тестируется как «иногда работает».
6. **Красный тест блокирует изменение** (правило процесса, см.
   `DOCS/04-RULES-OF-CHANGE.md`).

## Формат тест-плана модуля

```
T-<модуль>-<номер>  <имя>
  Шаги: ...
  Эталон: ...
  Время: ...
```

## Уровни проверки для L0 (все три обязательны)

1. **Статический разбор** — поля образа сверяются со спецификацией.
2. **Дизассемблирование** — мнемоники и цели rip-смещений сверяются
   с замыслом (ловит ошибки кодировок).
3. **Эмуляция/запуск** — программа исполняется, вывод и код возврата
   сравниваются с эталоном (ловит ошибки логики).

Практика этапов E0–E2 подтверждает многоуровневую проверку:
E0 поймал три ошибки ручной сборки (байты ImageBase, бит mod в modrm,
порядок байтов disp32); E1 — ещё пять (метки IAT→INT, перепутанные
reg/rm в mov, mov вместо add, непропущенная кавычка argv[0], длина
в волатильном rcx); E2 — шесть (modrm-поля r12–r15 ×4, rol eax вместо
rol al, порядок проверок copy_word). Все ошибки E1/E2 пойманы только
исполнением (уровень 3) — разбор и дизассемблер их пропустили.
Уровень 3 обязателен.

## Этап E3: компилятор в контуре тестов

С этапа E3 главный интеграционный тест любого образа L0 — сборка его
.hex-листинга компилятором `hexgen.exe` и сверка с эталонным .exe по
хэшу/байтам (T-M4-02..06). Правка листинга без прогона этого круга —
незавершённое изменение.

## Этап E4: конвейер в контуре тестов

С этапа E4 сборка образа = два шага: `hexgen.exe <модуль>.hex` → тело;
`pegen.exe тело <модуль>.peg` → EXE. Итоговая сверка — fc /b с эталонным
.exe (T-M5-02..06; для pegen — самосборка T-M5-06). Заголовки вручную
не правятся: изменения обёртки — через `.peg` (SPEC/07).

## Этап E5a: автоматическая батарея LAB

С этапа E5a вся «пирамида» (кроме физического запуска на Windows)
исполняется автоматически: `python3 LAB/py/lab_verify.py` — 96
проверок за ~33 секунды (целостность SHA, инварианты PE SPEC/04,
эмуляция документированных сценариев TESTS/ уровня 3, равенство
оракулов ATOM/BRICK/PEG/ENC/SPLICE инструментам, круги E4, самохостинг
E5 на разрезе, оракул ENC, равенство enc.exe оракулу + самохостинг
E6.2 на разрезе, большие исходники, концы строк, оракул и инструмент
SPLICE, самохостинг E6.3, оракул WALL: якоря/ошибки/демо-круг/
PE-инварианты/big_source). Тяжёлые эмуляции (самохостинг
enc — ~11 млн шагов с шагом splice) дают основную долю времени; каждая
проверка остаётся детерминированной и воспроизводимой.
Ручные проверки на Windows остаются приёмочными для смены этапа;
между ними батарея — обязательный зелёный ценз каждого изменения.
С этапа E6.1 батарея также запускается автоматически GitHub Actions
при каждом пуше (`.github/workflows/verify.yml`): красная проверка CI
= незавершённое изменение.

## Этап E5: BRICK в контуре тестов

С этапа E5 модули слоя L1 ведут исходники в BRICK: сборка =
`brick.exe <модуль>.brick` → тело; `pegen.exe тело <модуль>.peg` → EXE.
Главный интеграционный тест BRICK — самохостинг: brick.exe(brick.brick)
== hexgen(brick.hex) байт-в-байт (T-M6-16). Канонический исходник модуля
L1 — `.brick`; `.hex` — равносильная ATOM-форма (сверяются кругом).

## Этап E6.4a: язык в контуре тестов

С этапа E6.4a язык WALL v1 (SPEC/11) верифицируется оракулом LAB до
создания инструмента: якоря компиляции выписываются вручную
(`LAB/py/lab_l2_cases.py`: 4 полных выхода + 6 фрагментов) — второй
независимый свидетель; ошибки — с точными номерами строк (26 случаев);
главный интеграционный тест — полный круг WALL -> enc -> brick -> pegen
-> эмуляция (T-E6-21, «U-WALL-OK 37»); PE-инварианты демо — по SPEC/11
(вход 0x1200 — зафиксированное отклонение от SPEC/04). Правка оракула
без прогона батареи — незавершённое изменение; правка, меняющая выход,
требует пересчёта якорей вручную с записью в журнал находок
(T-L2-WALL.md). Инструмент wall.exe (E6.4b) будет обязан совпадать
с оракулом байт-в-байт на всех якорях и big_source.

## Этап E6.3: разрез в контуре тестов

С этапа E6.3 большие исходники L1 собираются из частей: сборка =
`splice.exe <модуль>.b2` → плоская форма → `enc` → `brick` → `pegen`.
Главные интеграционные тести разреза: (1) splice(корень) == плоская
форма == оригинал до разреза (T-E6-17, сверка с оракулом на реальных
корнях); (2) тела не изменились — круги E5/E6.2 зелёные на разрезе;
(3) самохостинг splice из собственного разреза (T-E6-18). Правка
любой части без прогона батареи — незавершённое изменение.

## Этап E6.4b: инструмент wall.exe в контуре тестов

Инструмент M2-WALL (KERNEL/L2-WALL) проверяется секцией 10 батареи
(lab_t_wall2.py): T-E6-25 справка; T-E6-26 все якоря компиляции —
wall.exe == оракулу байт-в-байт; T-E6-27 отвержение 26 программ с
номерами строк; T-E6-28 полный круг wall -> enc -> brick -> pegen ->
эмуляция («U-WALL-OK 37»); T-E6-29 big_source == оракулу; T-E6-30
SHA-256 + PE-инварианты. Любая правка KERNEL/L2-WALL/ без зелёного
прогона батареи (105/105) — незавершённое изменение; SHA в
lab_verify.py обновляется вместе с артефактом.
