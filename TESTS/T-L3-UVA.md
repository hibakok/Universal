# T-L3-UVA. Тест-план ассемблера uva.exe (M3-UVA)

Паспорт файла: TESTS/T-L3-UVA.md | слой: L3 | роль: тест-план модуля M3-UVA.

Обязательство модуля (SPEC/12 п. 8, этапы E7.3 (ЗАКРЫТ) + E7.4-3a):
выход uva.exe == ассемблеру оракула `LAB/py/lab_vm.py` (`assemble`)
байт-в-байт на всех валидных исходниках класса срезов; отвержение —
с теми же номерами строк, что `AsmError.line` оракула. Срезы 1
(E7.3-1): класс = `.mem` + `halt`; срез 2 (E7.3-2): + F1 — `mov`/9 АЛУ
с регистрами r0..r15; срез 3 (E7.3-3): + F2 — `const` и `ldb/stb/
ldq/stq` с операндами памяти rA[+смещ]; срез 4 (E7.3-4): + F3 —
`jmp`/`jnz` с целями метка/число и МЕТКИ (полный класс v0; приёмка
DoD этапа — T-E7-25); срез 5 (E7.4-3a): + МНЕМОНИКИ v1 — `mul/div/
mod/sra` (F1, 3 операнда), `call` (F3, цель метка|число) и `ret`
(F0 — 1 байт, 0 операндов). Директива .data и контейнер .UP v2 —
срез E7.4-3b (очередь).

Автоматизация: все тесты — батарея (секция 15, `LAB/py/lab_t_uva.py`);
запуск `python3 LAB/py/lab_verify.py` (группа 3: `python3
LAB/ai/battery_groups.py 3`). Время: секунды на проверку (кроме
сборки ~80,5 млн шагов эмуляции — T-E7-19).

## T-E7-24. Сквозной круг uva → kernel.exe + детерминизм

Шаги: uva.exe собирает `.mem 8`+`halt 42`, `.mem 0`+`halt 37`,

r2`+`halt 7` (F1), `.mem 8`+`const r1, 8`+`const r2, 65`+`stb r1+0,
r2`+`halt 0` (F2: вывод 'A' в консоль окном устройств), `.mem
4096`+const/stq/ldq/add/stb-в-консоль (F2 целиком: 'F'), `.mem 8`+

Эталон: коды возврата ядра 42/37/0/7/0/0/5/2/0/5, консоль

## Журнал находок

- **Дефект №24 (оракул lab_vm, закрыт E7.3-1):** строка из одних
  разделителей/запятых (",,,") — `_toks` возвращал пустой список,
  `toks[0]` — крах IndexError (не AsmError). Фикс: пустые токены =
  пустая строка (пропуск) — как uva.exe по построению; корпус
  T-E7-21 «sep line» и T-E7-23 «.mem + разделители» зафиксировали.
- **Урок E7.3-1 (собственный исходник):** идиома `while go == 1 /
  go = line_next() / тело` выполняет тело и при go == 0 (условие
  проверяется только в голове цикла) — последняя строка без хвостового
  LF кодировалась дважды (поймано T-E7-21 «no final lf»: codesize 12
  вместо 6; локализовано трассировкой эмулятора). Идиома итератора
  в WALL — чтение ВПЕРЁД: `go = line_next() / while go == 1 / тело /
  go = line_next()` (задокументировано в шапках pass1/pass2).
- **Наблюдение E7.3-2:** номера строк ошибок совпадают с оракулом и на
  невалидных операндах F2-строк (const/ldb/stb/ldq/stq) до реализации
  срезов 3-4 — оба отвергают на строке инструкции (случай «mov +
  константа r16 позже»); валидные F2-программы в корпус не входят
  (оракул собирает, uva — ещё нет).
- **Решение E7.3-3 (семантика смещений):** смещение операнда памяти
  у оракула БЕЗ проверки диапазона (int() в _memop — в отличие от
  _num) — маскируется _i32 при кодировании; uva копит величину
  mod 2^64 (перенос imul/add не ошибка) — гомоморфизм колец
  гарантирует те же младшие 32 бита, что у bigint-оракула
  (зафиксировано корпусом: 2^32, 10^20 — байт-в-байт).
- **Наблюдение E7.3-3 (бэктрекинг regex):** операнд r11 голый —
  валиден (r([0-9]|1[0-5]): сначала ветка rN, откат на r1X), r16/r19 —
  нет; последовательный разбор uva повторяет откат явно (ветка A3
  в parse_memop) — корпус «ldb r11 bare»/«r19» фиксирует.
