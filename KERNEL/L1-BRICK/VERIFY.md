# Проверка модуля M1-BRICK

Паспорт файла: KERNEL/L1-BRICK/VERIFY.md | слой: L1 | роль: инструкция проверки.

## Паспорт артефакта

| Свойство | Значение |
|---|---|
| Файл | `KERNEL/L1-BRICK/brick.exe` |
| Размер | 3584 байта (0xE00) |
| SHA-256 | `5F7F9EFD3398B735E762B37610ED1F197C383DA7252A3CD0C73DD3EE31A5C857` |
| Тип | PE32+ (консоль, x86-64), 1 секция + bss, импорт kernel32.dll |
| Исходники | `brick.hex` (ATOM L0, бутстрап) и `brick.brick` (BRICK v1, канонический) + `brick.peg` |

## Проверка 1: подлинность (хэш)

```
certutil -hashfile brick.exe SHA256
```

Должно совпасть с SHA-256 из таблицы выше.

## Проверка 2: справка

```
brick.exe
```

Ожидаемый вывод (46 байт + CRLF): `U-L1-BRICK CMDS: BRICK <SRC.BRICK> <OUT.BIN>`
Код возврата: 2.

## Проверка 3: коды возврата

Таблица кодов — SPEC/08 (2..10). Сценарии — тест-план `TESTS/T-L1-BRICK.md`
(T-M6-07..15).

## Проверка 4: самохостинг (DoD этапа E5 — главный тест)

```
Из папки KERNEL:
  L1-BRICK\brick.exe L1-BRICK\brick.brick t_self.bin
  L0-HEXGEN\hexgen.exe L1-BRICK\brick.hex t_body.bin
  fc /b t_self.bin t_body.bin        ->  различий нет (2968 байт)
  L0-PEGEN\pegen.exe t_self.bin L1-BRICK\brick.peg t_brick.exe
  fc /b t_brick.exe L1-BRICK\brick.exe  ->  различий нет
```

Третья строка — сам DoD: ассемблер собирает себя из собственного
BRICK-исходника. Пятая — полный круг воспроизводства из текстов.

## Пойманные ошибки ручной сборки (все — уровнем 3/4, эмуляция и оракул)

Уроки E5 (подтверждение практики E0–E4: уровень 3 обязателен; дизассемблер
пропускает почти всё — кодировки были валидны, но неверны):

1. **REX-биты R/B** (5 ошибок): `add r9,r11` собран как 4C (R) вместо 4D
   (R+B); `sub rax,r10` — 4C вместо 49 (B); `mov r11d,ecx` — 44 (R) вместо
   41 (B); `sub r15,r10` — форма 2B вместо 29 (приёмник/источник меняются
   местами); `mov [r9],rax` — 48 вместо 49. Правило: reg-поле → R, rm-поле
   → B, и для пары старших регистров нужны ОБА бита.
2. **modrm-поля**: `cmp r8b,[rdx]` — modrm 10 ([rax]) вместо 02 ([rdx]);
   `mov r11,[r14]` — 1A ([r10]) вместо 1E ([r14]).
3. **inc rsi/rdi**: 7 мест с байтом C7 (inc rdi) вместо C6 (inc rsi) —
   пути разбора молча съедали первый символ.
4. **Затирание результата**: `pop rax` после `call find_label` уничтожал
   результат поиска (define_label); исправлено пересылкой в r11 до
   восстановления аргументов.
5. **Затирание rax-аргумента**: `movzx eax,[rsi]` в проверке суффикса
   `:1` затирал адрес имени (parse_h); переведено на r9.
6. **Затирание rdx-поиска**: цикл сравнения в find_label использовал rdx
   для адреса имени записи — длина поиска терялась; переведено на r11
   с сохранением r11 через стек (r11 занят у вызывающих: ширина DD/DQ,
   размер слота).
7. **Файловая длина**: parse_dbz сохранял абсолютный rdi вместо
   относительного (r15 = rdi − r10).
8. **Индексы errtab**: 5 ветвей ошибок диспетчера смещены на 1 (печатали
   чужие строки); правило: индекс = порядковый номер записи в errtab.
9. **Слот не в конце строки**: формы `81 3D disp32 imm32` и `C7 05 disp32
   imm32` имеют байты ПОСЛЕ слота — противоречие SPEC/08 («слот последний»);
   переписаны эквивалентами со слотом в конце (`mov eax,X; cmp eax,imm32`).
10. **Запись DZ в пассаже 1**: нули материализовались до проверки предела
    (переполнение imagebuf на телах > 64 КиБ); пассаж 1 теперь только
    сдвигает курсор, imagebuf расширен до 0x20010.
11. **Пропуск предопределённой base**: таблица меток не инициализировалась
    записью base = −0x1000 до пассажа 1.
12. **[E5a, найдено лабораторией LAB]** hex16_to_4 (K1-H001) читал
    только биты 16..31 eax: 4 ротации по 4 бита покрывают лишь старшую
    половину регистра, а номер строки (≤ 0xFFFF) лежал в младшей —
    ERR=FORMAT AT= всегда печатался как 0000 для строк 1..65535.
    Эмуляция E5 пропустила это (ожидала нули в номере), оракул LAB
    поймал сверкой типов/номеров ошибок. Исправление: `shl eax,16`
    в начале hex16_to_4 (тело 0x73B); тогда же DZ 1 после имени DLL
    для чётности hint-RVA. Тело 0xB94 -> 0xB98.
13. **[E5a, найдено лабораторией LAB]** пустые DB/DD/DQ принимаются
    молча (SPEC/08 обещает ошибку «пустой список») — отклонение
    зафиксировано, исправление отложено до BRICK v2 (этап E6).
14. **[E5a, найдено лабораторией LAB]** опечатка в README: SHA-256
    pegen.exe был обрезан на 1 символ.

Вывод: эмуляция + оракул (двойная независимая реализация семантики) —
обязательные уровни для каждого образа; objdump ловит только грубые
нарушения кодировок.

## Соответствие этапной методике

- До кода созданы карточки-план (правило R3): ветви A/T/N спроектированы
  в SPEC/08 и CARD.md до материализации.
- Ведомость E5 (внешний инструмент сессии): один источник истины ->
  и brick.hex, и brick.brick; сверены оракулом, hexgen и brick.exe
  (четыре независимых материализации дают идентичные 2968 байт).
- С этапа E5а вся верификация доступна одной командой:
  `python3 LAB/py/lab_verify.py` (67 проверок, ~7 с).
