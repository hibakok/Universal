# Проверка модуля M0-HXDUMP

Паспорт файла: KERNEL/L0-HXDUMP/VERIFY.md | слой: L0 | роль: инструкция проверки.

## Паспорт артефакта

| Свойство | Значение |
|---|---|
| Файл | `KERNEL/L0-HXDUMP/hxdump.exe` |
| Размер | 3584 байта (0xE00) |
| SHA-256 | `F0CEE97E45B1399FF13151BF4587BA2A02465E793FB9C92F525CDD69A7B4A8E3` |
| Тип | PE32+ (консоль, x86-64), 1 секция, импорт kernel32.dll (7 функций) |
| Исходники | `hxdump.hex` (тело секции, ATOM v1, телесная форма) + `hxdump.peg` (обёртка, SPEC/07) |
| Использование | `hxdump.exe <файл>` (см. CARD.md) |

## Проверка 1: подлинность (хэш)

```
certutil -hashfile hxdump.exe SHA256
```

Вывод должен совпасть с SHA-256 из таблицы выше (регистр не важен).

## Проверка 2: дамп известного файла

```
KERNEL\L0-HXDUMP\hxdump.exe KERNEL\L0-SEED\seed.exe
```

Первые две строки (строго, байт-в-байт):

```
00000000: 4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00  MZ..............
00000010: B8 00 00 00 00 00 00 00 40 00 00 00 00 00 00 00  ........@.......
```

Каждая строка завершается CRLF. Всего строк: 64 (1024 байта / 16).
Последняя строка начинается с `000003F0:`.

## Проверка 3: коды возврата

```
hxdump.exe seed.exe            → echo %errorlevel%  → 0
hxdump.exe                     → echo %errorlevel%  → 2
hxdump.exe no_such_file.bin    → echo %errorlevel%  → 4
```

## Проверка 4: соответствие листингу

Контрольные байты (тест T-M3-12, `TESTS/T-L0-HXDUMP.md`).

## Сборка (с этапа E4)

```
hexgen.exe hxdump.hex  t_body.bin
pegen.exe  t_body.bin  hxdump.peg  t.exe
fc /b t.exe hxdump.exe   ->  различий нет
```

Полный круг «текст → EXE» — `T-M5-04` в `TESTS/T-L0-PEGEN.md`
(заголовки генерирует pegen из `hxdump.peg`; SHA-256 артефакта не изменился).

## Журнал верификации

| Дата | Кто | Уровни | Результат |
|---|---|---|---|
| Этап E2 | ИИ (GLM) | PE-разбор (30 инвариантов) + objdump (244 инструкции, без (bad)) + эмуляция (12 прогонов, 143–139 212 шагов; эталон дампа — независимый генератор) | все зелёные |

Эмулятор перед прогоном hxdump был повторно валидирован на `seed.exe`
и `seed2.exe` (16 прогонов этапов E0/E1 воспроизведены).

## Пойманные ошибки сборки (почему нужна трёхуровневая проверка)

Эмуляция уровня 3 поймала шесть реальных дефектов, прозёванных
разбором и дизассемблированием:

1. `mov r13d,r14d` был закодирован с перепутанным полем rm modrm
   (получился no-op `mov r13d,r13d`) — строка дампа всегда печатала
   16 байт, счётчик не убывал. Класс ошибки E1 (reg/rm), теперь в
   регистре r13/r14.
2. `cmp r14d,16` — та же ошибка rm: сравнивался r12d.
3. `sub r14,r13` был закодирован как `sub r15,r13` (rm=111+B = r15).
4. `mov eax,r15d` был закодирован как `mov eax,r13d` (reg=101+R).
5. Алгоритм H022 использовал `rol eax,4` (32-битную ротацию) вместо
   `rol al,4` (8-битную): старшая тетрада байта не попадала в младшие
   биты — hex-цифры были неверными при верной ASCII-колонке.
6. Проверка длины имени срабатывала до проверки конца слова: имя ровно
   из 127 байт ошибочно считалось длинным (порядок проверок в C014
   изменён: сначала конец слова, потом вместимость).

Каждая ошибка — класс «кодировка/порядок», ловимый только исполнением.
Вывод: уровень 3 обязателен для каждого образа L0 (правило SPEC/02).

## Замечания

- Файл не подписан: SmartScreen/антивирус могут спросить подтверждение.
- Программа только читает указанный файл: ничего не изменяет и не
  пишет на диск; сеть не использует.
- Работает на Windows 7+ x64 и под Wine.
