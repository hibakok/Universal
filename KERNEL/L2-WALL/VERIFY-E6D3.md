# VERIFY. Модуль M2-WALL — этап E6.4d-4/2 (фикс №19)

Паспорт файла: KERNEL/L2-WALL/VERIFY-E6D3.md | слой: L2 | роль:
журнал верификации шага E6.4d-4/2 — закрытие дефекта №19 (вложенные
вызовы в аргументах + call-утверждения с выражениями).

## 1. Постановка

План сессии 28, пункт (1): дефект №19 починить ДО прохода 2 — каркас
должен компилироваться без обходов («max2 порознь»). Вход: батарея
131/131 (E6.4d-4/1 закрыт).

## 2. Диагностика — дефект оказался ТРЁХСТОРОННИМ

1. **(а) wall.exe отвергал вложенные вызовы в аргументах** —
   f(x, f(x,1)+1): ERR=FORMAT. Причина: tmp5 (счёт аргументов) и
   tmp6 (max need) — ГЛОБАЛИ; вложенный p_args обнулял их,
   затирая состояние объемлющего вызова; итоговый счёт шлифовал
   arity-проверка p_call_tail → ERR=FORMAT (старая запись
   VERIFY-E6D2 §7).
2. **(б) ОРАКУЛ ПРИНИМАЛ, НО ЭМИТИЛ НЕВЕРНЫЙ КОД** — вложенный
   вызов стейджил свои аргументы в C1.. — ЗАТИРАЛ уже застейдженные
   C-слоты объемлющего; загрузки объемлющего читали аргументы
   вложенного. Пример: f(y, g(x,1)+1) — внешний вызов получал x
   вместо y. Полный круг эмуляцией: старый оракул печатал
   «U-NEST-OK 54» (неверно), новый — «U-NEST-OK 4C» (=76, верно).
3. **(в) ЛАТЕНТНЫЙ ДЕФЕКТ maxd call-УТВЕРЖДЕНИЙ (с E6.4a!)** —
   _scan оракула (lab_l2_lay) и S00D wall.exe не учитывали need
   аргументов вызова-УТВЕРЖДЕНИЯ (только присваивания/return/
   setb/astore): T-слот T(1) налезал на C(1). Пример: f(y, 1+2) —
   стейджинг левого операнда bin затирал y; f получала «1».
   НИ ОДИН якорь/корпус не содержал такого утверждения — дефект
   жил 6 этапов. Пойман ручной трассировкой при проектировании
   фикса (сканер scripts/scan_compat — не часть репозитория).

Сторона истины: грамматика SPEC/11 п.2 разрешала вложенные вызовы
ВСЕГДА (вызов — первичное; аргументы — выражения); п.5 требовал
«учёт вложенных вызовов обязателен». Дефект был на стороне
РЕАЛИЗАЦИИ обеих инструментов (и оракула!).

## 3. Канон (SPEC/11 п.5/8, фикс)

- База: вызов, начинающийся, когда объемлющий застейджил j
  аргументов, получает base = base_объемлющего + j; аргумент i
  стейджится в C(base+i); загрузки — из тех же слотов; после
  закрытия вложенного его слоты мертвы и переиспользуются.
- maxc = max по вызовам (base + n) [ext: base + min(n,4)] —
  одновременное использование C-слотов объемлющего и вложенного.
- maxd call-утверждения = need(вызова) = max need аргументов —
  как присваивание.
- Обратная совместимость: без вложенных вызовов и без call-
  утверждений с need>0 — все базы 0, maxd не растёт: выход
  байт-в-байт (проверено на 59 исходниках: якоря/DEMO/big,
  старый против нового оракула — 0 различий).

## 4. Реализация

- **Оракул**: lab_l2_lay.py (cact/ccur в Layout._call + _upd для
  call-утверждений), lab_l2_gen.py (cact/ccur в Gen.call; c(i) →
  c(base+i), загрузки с базой).
- **wall.exe** (wall_pa.b2 + wall_pp.b2 + wall_p1s.b2):
  P014 p_args — счёт/max/база в РАМКЕ (d/base/cnt/mx/eflg/need);
  глобальные pc_cact [r13+18050] (вложенность; вход: base :=
  pc_staged при pc_cact>0), pc_staged [181F8] (стейджинг самого
  внутреннего АКТИВНОГО; выход: восстановление), pc_cbase [18078]
  + tmp5 [181E8] (база/счёт закрытого вызова — интерфейс P015/
  P016); выход: RAX = max need. Скаляры — реюз мёртвых слотов
  (tok_kind/pc_d/tmp7 — grep-аудит использования: 0). P017
  pa_stage — только эмит: слот C(base+cnt+1), 5-й аргумент ext →
  S5; P015 — загрузки C(pc_cbase+i); P016 — maxc = pc_cbase+n;
  P013a — need из рамки [rbp-20]; S00D — st_maxd = max(need).
  Каркас (wall_self_pa/p1s/pp.wall + wall.wall): локали рамки
  p_args, call_stats с pc_cbase, p1_namestmt maxd; pa_stage
  каркаса удалена (эмит-механика — проход 2).
- **Артефакты**: EXE 27648 → 28160 Б (тело 26998 → 27262, +0x10C);
  метки 581 → 585 вкл. base (+5 pa_top/pa_base/pa_l1/pa_l2/p1c_md,
  −1 pas_st); M-строки 5128 → 5189; SHA 8541FD9D… → E04BA41B…;
  пересборка LAB/ai/wall_build.py (splice → enc → brick → pegen,
  оракульные сверки на каждом шаге).

## 5. Верификация

- Якоря F17 (вложенные вызовы) и F18 (call-утверждение с bin-
  аргументом) — ВРУЧНУЮ по SPEC/11 (независимо от оракула) —
  совпали байт-в-байт с новым оракулом и wall.exe (T-E6-26).
- DEMO_NEST («U-NEST-OK 4C») — полный круг wall → enc → brick →
  pegen → эмуляция: T-E6-51; семантика подтверждена ручным
  счётом (8+6=14, +17=31, +6=37, +39=76=0x4C); СТАРЫЙ оракул на
  том же исходнике печатает «U-NEST-OK 54» — канарейка ловит
  класс дефекта, а не случайное совпадение.
- Корпус T-E6-49d: 178 → 180 записей (F17/F18 вошли автоматически
  через CASES_FRAG), сравнимо 161 → 163 — трёхсторонние канарейки
  (оракул parse == каркас == wall.exe).
- Батарея 131 → 132/132 (~95 с). Регресс: 59 старых исходников —
  байт-в-байт (совместимость v1/v2); каркас wall.wall == оракулу
  байт-в-байт (T-E6-49a — оба пересчитаны синхронно: framesize
  функций каркаса с call-утверждениями need>0 выросли по НОВОМУ
  канону — 27 таких утверждений в исходниках каркаса).
- Инструмент LAB/ai/bytecode_rows.py — перенос адресов карты
  ветвей BYTECODE.md §2 по якорям-меткам (старый/новый .brick);
  ПОЙМАН накопленный дрейф документации: 26 строк §2 не
  соответствовали даже СТАРОЙ сборке (частичные обновления
  прошлых сессий; кластеры +6/+0x100/+0x60E/+0x7A0). Все строки
  приведены к НОВОЙ карте (старты — по меткам, концы — по
  следующим кирпичам; полная ревизия формата карты — очередь).
