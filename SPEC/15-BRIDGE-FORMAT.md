# S15. Формат BRIDGE v1 (мост EXE -> BRICK v2 + PEG v1)

Паспорт файла: SPEC/15-BRIDGE-FORMAT.md | слой: L5 | роль: спецификация
моста — вход чужому машинному коду в мир UNIVERSAL (этап E9).

## Назначение

Мост L5 превращает готовый EXE обратно в ИСХОДНИК нашего конвейера:
тело секции становится текстом BRICK v2 (SPEC/09), обёртка — текстом
PEG v1 (SPEC/07). Круг `enc -> brick -> pegen` на выходе моста обязан
давать EXE, байт-в-байт равный исходному (DoD среза E9.1 — все
артефакты семейства; прецедент «сначала истина семантики» E7.1/E8.1:
спецификация и оракул `LAB/py/lab_bridge.py` ДО инструмента bridge.exe,
который появится срезом E9.2+ как модуль KERNEL/L5-BRIDGE).

Срезы: **v1 (E9.1)** — образы СЕМЕЙСТВА UNIVERSAL (собраны pegen по
SPEC/04: одна секция .text на RVA 0x1000, один kernel32.dll, DOS-заглушка
шаблона). Чужие EXE (другие заголовки/секции/DLL) — срезы E9.4+.

## п. 2. Контракт входа

Принимаются образы, удовлетворяющие инвариантам SPEC/04 (проверка
`lab_pe.check_spec04`), кроме двух легальных отклонений семейства:
точка входа 0x1200 (wall/kernel/uva — SPEC/11 п. 6) и RawSize,
превышающий VirtualSize (файл дополнен выравниванием). Всё остальное
(в т.ч. пустые импорты-заглушки) — BridgeError. Имя модуля читается из
DOS-заглушки `Universal L0 <имя>. No DOS support.` (шаблон pegen).

## п. 3. Обнаружение кода (детерминизм R8)

1. Старт: точка входа. Кандидаты: цели `jmp`/`jcc`/`call rel32`
   (прямые). Косвенный `call [rip+...]` новых кандидатов не даёт —
   его цель слот IAT (п. 6). Косвенный `jmp` (FF /4, E9.4-1) —
   ТЕРМИНАЛ: цель — значение операнда, вычислить её без исполнения
   нельзя; кандидаты — ТОЛЬКО таблица переходов (E9.4-2): форма
   `jmp qword [rip+X]` с X в данных даёт цели-кандидаты из
   qword-строк данных — читаются ПОДРЯД от X, значение —
   кандидат, пока оно адрес кода (`0 < v < VirtualSize`);
   терминатор — первый non-code qword (0 или вне тела) либо конец
   тела (за target — виртуальные нули: вилка raw/bss).
   Регистровая/индексная форма (`jmp r64`, `[base+idx]`) —
   терминал без кандидатов. Граница (E9.4-2): кандидат,
   декодирующийся за пределы VirtualSize, — BridgeError (не
   семейство); для v1-семейства случай невозможен (FF /4 в
   семействе нет), для чужих EXE — риск, пересмотр в срезе порта.
2. Путь читается линейно до обрыва: терминал `jmp`/`ret`/`int3`;
   сбой декодирования (декодер SPEC/05, `lab_x86`); выход за пределы
   тела; инструкция из ОДНИХ НУЛЕВЫХ байтов (нули — данные: реальных
   инструкций из одних нулей в семействе нет, а падение в выравнивающие
   нули кода исключается).
3. Тень: если два пути декодируют пересекающиеся байты, побеждает
   инструкция с МЛАДШИМ адресом (проход по возрастанию с курсором).
4. Инструкция, выходящая за VirtualSize, — BridgeError (не семейство).

## п. 4. Метки

| Имя | Смещение | Смысл |
|---|---|---|
| `l<rva>` | старт инструкции | цель прямого перехода/вызова |
| `d<rva>` | свободный байт данных | цель rip-ссылки |
| `iat_<имя>` | слот IAT | точка вызова импорта (имя — из записи импорта, строчными, [a-z0-9_]) |
| `$base` | предопределена (SPEC/08 п. 4) | rip-ссылка на RVA 0 |

- `<rva>` — шестнадцатеричные СТРОЧНЫЕ цифры (алфавит имён BRICK:
  [a-z0-9_]); например `l102b`, `d11ac`.
- Приоритет при совпадении смещения: `iat_` > `l` > `d` (первый
  записавший выигрывает; все ссылки на смещение используют одно имя).
- Метка НЕВОЗМОЖНА (и ссылающаяся инструкция берёт H-форму, п. 5),
  если цель: вне тела (кроме RVA 0 — это `$base`), строго внутри
  байтов другой инструкции или строго внутри семантической строки
  (п. 6). Метки эмитируются только там, где на них есть ссылки (плюс
  канонические метки импортов п. 6) — минимум имён.
- ПРАВИЛО ПРЕДСТАВИМОСТИ (E9.2-3b) распространяется и на
  канонические метки импортов п. 6: `iat_`/`d*` НЕ создаются, если их
  смещение строго внутри байтов выжившей инструкции (разрез попал бы
  внутрь уже покрытых байтов — наложение строк, невалидный b2);
  не-созданная метка не попадает в $ссылки и known-массив (значения
  DD остаются hex-текстом), а DQ-таблица с ссылкой на неё — сырыми
  байтами. Суффикс `iat_` — san: ТОЛЬКО ASCII [a-z0-9_] (прочие байты
  имени, вкл. латиницу-1, — «_»; нижний регистр; обрезка 59; пусто —
  «f»; имя вне файла — «?» -> «_»).

## п. 5. M-строки и H-фолбэк

M-строка эмитится ТОГДА И ТОЛЬКО ТОГДА, когда кодировщик enc (SPEC/09,
оракул `lab_enc.encode_m`) воспроизводит инструкцию ТОЧНО:

1. мнемоника и операнды отображаются из декодированного кортежа
   (регистры — имена из таблицы enc; числа — ЗАГЛАВНЫЙ hex со знаком
   «-»; память `[base+idx±disp]`, `[rip+$имя]`; размерное слово
   `byte/word/dword/qword` — только когда второй операнд
   непосредственный или мнемоника movzx);
2. слот rel8 (`$имя:1`) выбирается, если исходная инструкция короткая
   (jmp/jcc длиной 2), иначе слот 4 байта;
3. контроль: все фиксированные байты равны, слот последний в строке,
   исходное значение слота == `L(метки) − конец слота` (иначе
   кодировка enc не воспроизводит инструкцию).

При любом несоответствии (в т.ч. формы вне канона enc: короткие опкоды
`25/3C/05/3D`, movabs r64,imm64, jp/jnp, масштаб SIB != 1, 16-битные
регистры, cdq) эмитится **H-строка**: сырые байты + комментарий
`@<смещение>` и дизассемблерный текст с сырыми адресами. Байто-точность
круга сохраняется ВСЕГДА — H-фолбэк это вопрос читаемости, не корректности.

## п. 6. Данные и структуры импорта

Байты, не покрытые инструкциями, эмитятся по возрастанию смещений:

- `DB` — до 16 байт на строку (пробег нулей короче 3 входит в DB);
- `DZ <n>` — пробег из >= 3 нулей;
- `DD`/`DQ` с `$ссылками` — КАНОНИЧЕСКИЕ строки структур импорта
  (места, которые знает разбор lab_pe): дескриптор IDT (5 значений:
  INT/0/0/имя DLL/IAT — как $ссылки), таблицы твонков IAT и INT (по
  одной записи DQ на строку: $ссылка на запись имени, терминатор `0`).
  Значение становится $ссылкой только при точном совпадении с известной
  RVA; записи имён (hint+имя), имя DLL, старты массивов и слоты IAT
  получают метки п. 4. Любое отклонение от ожидаемой раскладки — строка
  падает обратно на DB/DZ (байты те же). Дополнительно (E9.2-3b):
  строка DD/DQ НЕ принимается, если строго внутри её байтов лежит метка
  (наложение разрезов); таблица DQ валидна только при СОЗДАННЫХ метках
  всех hint-записей (правило представимости п. 4); пустая таблица
  функций (n = 0) ДОПУСТИМА — DD + DQ `0` терминатора, метки имени
  DLL/INT без iat_-слотов.

## п. 7. Длина тела и !bss

`target = max(последний ненулевой байт + 1, концы всех инструкций)`;
если `align(target, 0x200) != SizeOfRawData`, target поднимается до
`SizeOfRawData − 0x1FF` (минимальная длина той же выравнивающей вилки).
Требуется `target <= VirtualSize`; тогда `!bss = VirtualSize − target`.
Хвостовые нули тела переходят в виртуальные нули — все поля,
вычисляемые pegen (SizeOfCode, SizeOfRawData, VirtualSize,
SizeOfImage), совпадают с исходными, круг байт-в-байт.

## п. 8. Регенерация PEG v1

`;`-шапка + `!module <имя из заглушки>`; `!entry`, `!idata`, `!iat` —
из полей образа (hex без 0x); `!bss` — п. 7 (опущена при 0);
`!stackcom`/`!heapcom` — из полей 0xE8/0xF8, опущены при значениях по
умолчанию 0x1000. Текст PEG моста может отличаться от исходного .peg
файла модуля (перенос хвостовых нулей в !bss; канонический порядок) —
критерий истины: собранный EXE, не текст.

## п. 9. Круг (DoD среза E9.1)

Для каждого артефакта семейства (все 11 модулей KERNEL):
`pegen(brick(enc(bridge_b2)), bridge_peg) == исходный EXE` байт-в-байт.
Ожидаемое качество: артефакты, собранные конвейером enc+brick+pegen
(kernel, uva — и их тела) — 0 H-строк; hand-made артефакты (seed,
seed2, hxdump, hexgen, pegen, brick) и исторические кодировки —
H-фолбэки неканонических форм. Свидетели: секция 18 батареи
(TESTS/T-L5-BRIDGE.md, T-E9-01..16) — оракул, якоря и сквозные круги
реальными инструментами.

## п. 11. Якоря репозитория (E9.3)

Выход моста над каждым артефактом семейства зафиксирован в репозитории
статическими файлами-якорями (прецедент листингов .hex у L0):

- `KERNEL/<м>/<имя>.anchor.b2` — канон текста тела (п. 4-6);
- `KERNEL/<м>/<имя>.anchor.peg` — обёртка PEG v1 (п. 8).

Якорь байт-в-байт равен выходу оракула (следовательно и выходу
инструмента: равенство «инструмент == оракул» на том же корпусе
доказано батареей — T-E9-22/24). Тем самым якорь фиксирует
ОДНОВРЕМЕННО оракул, артефакт и инструмент; изменение любого из них
видно как diff якоря в git. Свидетель — T-E9-25 (секция 18b,
`LAB/py/lab_t_anchor.py`: выход оракула == файлу, 12 артефактов;
чистый Python — без эмуляции). Регенерация — ТОЛЬКО намеренная
(`LAB/ai/anchor_gen.py`, отдельный коммит с зелёным T-E9-25);
случайная регенерация = потеря свидетеля.

Решение по «замене листингов на выход моста» (п. 10): ОТКЛОНЕНО.
Листинг .hex — ИСТОЧНИК конвейера hexgen (вход сборки L0-модулей),
якорь — СВИДЕТЕЛЬ выхода моста; смешение ролей меняет проверенный
