## Этап 8 — Библиотека L4 (открыт; цель — DoD: библиотека
используется минимум двумя разными программами)

### E8.1 (сессия 61) — SPEC/14 + оракул: «сначала истина семантики»

Прецедент E7.1/E6.1/E6.4a: спецификация и оракул ДО реализации
(этапы 8.2+). ЯДРО И АРТЕФАКТЫ KERNEL/ НЕ МЕНЯЛИСЬ — добавлены
спецификация, оракул LAB, реестр карточек и секция 16 батареи.

1. **SPEC/14-L4-LIBRARY.md** — спецификация библиотеки L4:
   - **Композиция (п. 2):** программа-потребитель — исходник .uva с
     `!include ../../KERNEL/L4-LIB/lib_*.uva`; склейка splice.exe
     (SPEC/10 — текстовый трансформатор, работает с любым
     построчным текстом; прецедент E6.3 — инструменты не меняются,
     ассемблер uva.exe не тронут) → uva.exe → .UP → kernel.exe.
     Части библиотеки — только инструкции/метки/комментарии (без
     .mem/.data — контейнер принадлежит программе). Метки кирпичей —
     префикс `lib_` (коллизии исключены конвенцией).
   - **ABI (п. 3):** аргументы r1..r4, результат r1; временные
     r1..r4; сохраняемые r5..r12; r13 = sp (SPEC/12 п. 3.4); r14 =
     devbase (программа ставит `const r14, <memsize>` до консольных
     кирпичей — devbase невычислим внутри библиотеки: memsize
     знает только программа); r15 — резерв. Вызов `call lib_*`,
     возврат `ret`; LIB-1 нерекурсивен; проверок аргументов НЕТ —
     их делает машина (ловушки 3/4; принцип явности SPEC/12 п. 2).
   - **Реестр LIB-1 (п. 4):** 11 кирпичей в 4 ветвях — C: chr_out,
     crlf_out, buf_out, buf_out_rev; N: u64_to_dec_rev (цифры с
     buf[0] = единицы, 0 → «0»), print_u64 (N001 + C004),
     print_i64 («-» + 2^64−v при v >= 2^63); S: str_len, str_out
     (до ПЕРВОГО NUL); M: mem_copy (формула по возрастанию —
     поведение при перекрытии определено), mem_fill (r2 AND 255).
   - **Рост (п. 7):** новые кирпичи = новые K4-*; ABI стабилен
     навсегда (как кодировка ISA); LIB-2 (окна/растр/ввод) — свои
     таблицы; кандидаты LIB-1: hex-печать, сравнение строк.
2. **Оракул** `LAB/py/lab_l4.py` (свидетель №1): эталонная
   семантика наблюдаемого результата каждого кирпича (консоль
   bytes / RAM bytearray / реверс-цифры); НЕ эмулирует UNIVM
   (это lab_vm.py) — моделирует контракт карточек SPEC/14 п. 4.
3. **Якоря** `LAB/py/lab_l4_cases.py` (свидетель №2): DEC 13
   (края разрядов: 0, 9/10, 99/100, 2^32±1, 2^63±, максимум
   2^64−1); I64 6 (край −2^63, −1, −10); REV 6 (вкл. 20-цифровый
   реверс максимума); STR 5 (хвост после NUL невидим); BUF 5
   (палиндром — прямой == обратный); CPY 6 (перекрытия ОБЕИХ
   направлений, n=0, dst=src); FILL 4 (0x141 → 0x41);
   CMP_U64 3 / CMP_I64 2 (композиция печать + CRLF).
4. **Секция 16 батареи** `LAB/py/lab_t_l4.py`: T-E8-01..07 —
   оракул == якорям (все группы). lab_verify.py: подключение секции
   + докстринг секций 13-15 сжат (482/500 строк); battery_groups.py:
   группа 3 = секции 13-16. **Батарея 180 → 187/187** (группа 3 —
   42/42; все секции мгновенны — чистый Python).
5. **Реестры:** MAP/M4-LIB.md — 11 карточек K4-* (статус «план» —
   карточки ДО кода, R3; состав поля Файл — будущие части
   KERNEL/L4-LIB/lib_{c,n,s,m}.uva); MAP/METHODS.md — раздел L4,
   +11 строк (497/500); TESTS/T-L4-LIB.md — тест-план модуля
   (обязательство + якоря + статус); MAP/LAYERS.md, MAP/INDEX.md,
   DOCS/02, README, LAB/README — статусы и счётчики.

Дефекты: 2 якоря выписаны неверно при ручной сверке ДО фиксации
(CPY «хвост» — ожидание не по формуле; CMP смешивал u64/i64 без
признака) — исправлены до подключения батареи; дефектом ОРАКУЛА
не являлись (оракул прав по SPEC). Пойманы локальным прогоном
свидетель-сверки до написания секции 16.

Решения (чтобы не передумывать):

1. **Композиция на уровне ТЕКСТА через существующий splice.exe**
   (не новый «линкер» и не правка uva.exe): .UP-контейнер не несёт
   меток/имён (SPEC/13 п. 5) — связывание возможно только до
   ассемблирования; текстовый склейщик уже есть (SPEC/10 прямо
   говорит: работает с любым построчным текстом); префикс lib_ —
   единственная конвенция пространства имён.
2. **r14 = devbase вместо вычисления** — memsize знает только
   программа (заголовок .UP её собственный); явность > удобство
   (принцип SPEC/12 п. 2): библиотека не «угадывает» базу окна.
3. **Реверс-цифры u64_to_dec_rev** (buf[0] = единицы): деление
   u64 даёт цифры от МЛАДШЕЙ — реверс-буфер естественен для
   кирпича-генератора; печать «старшая слева» — составной кирпич
   через buf_out_rev (кирпичность: сложное из простого).
4. **mem_copy — формулой по возрастанию** (не «неопределённое
   перекрытие»): детерминизм R8 требует однозначности; якоря
   покрывают оба направления перекрытия.
5. **Сначала оракул, реализации потом** (E8.2 по ветвям): якоря
   уже готовы — диффтест реализации подключается к ним же
   (консоль/RAM после прогона uva → kernel.exe, как секции 14/15).

Далее (E8.2, план сессии 62): первая реализация — ветвь C
(4 кирпича: chr_out, crlf_out, buf_out, buf_out_rev — самые
простые; .mem-буфер тест-программы, ABI r14) + диффтест-корпус
программ для секции 16 (прогон lab_vm.run_asm == оракул); затем
N (u64_to_dec_rev + составные), S, M; E8.3 — демо-программы DoD.

### E8.2a (сессия 62) — ветвь C: первая реализация библиотеки

План сессии 61 исполнен (ветвь C + диффтесты) и превзойдён:
добавлен СКВОЗНОЙ КРУГ РЕАЛЬНЫМИ ИНСТРУМЕНТАМИ (T-E8-11) —
доказательство композиции «программа + библиотека» всей цепочкой
репозитория без пересборки ядра. ЯДРО kernel.exe И ЕГО АРТЕФАКТЫ
НЕ МЕНЯЛИСЬ (R7: библиотека — внешние исходники).

1. **KERNEL/L4-LIB/lib_c.uva** (новый, 46 строк): 4 кирпича —
   `lib_chr_out` (stb r14+0 — атомарный, ничего не затирает),
   `lib_crlf_out` (две записи; затирает только временную r1),
   `lib_buf_out` / `lib_buf_out_rev` (циклы «осталось < 1?» —
   lt/jnz; прямая печать указателем p++, обратная — индексом
   «осталось−1»; затирают только r1..r4 — временные ABI).
   Идиома ветви C: единственный регистр шага r3 = 1 задаётся ДО
   цикла — внутри цикла нет ни одной константы (короче и
   симметрично обоим кирпичам); условие выхода `lt r4, r2, r3` —
   len=0 корректен без специальных ветвей. r0 не используется вовсе —
   он не классифицирован ABI SPEC/14 п. 3 (осторожность).
2. **KERNEL/L4-LIB/CARD.md** (новый, 70 строк): карточка модуля
   M4-LIB — рецепт композиции (порядок ОБЯЗАТЕЛЕН: .mem/.data ->
   код программы -> halt -> !include частей; два основания:
   исполнение со смещения 0 и «.mem до первой инструкции»
   SPEC/12 п. 8), состав ветвей, ABI, верификация.
3. **SPEC/14 п. 2 — уточнение положения !include** (ПОСЛЕ кода
   программы; без перенумерации пунктов — ссылки «ABI п. 3»
   везде живы): найдено при реализации, зафиксировано в SPEC
   (истина) и в CARD.md (рецепт).
4. **Диффтесты T-E8-08..11** (`LAB/py/lab_t_l4.py`, 107 → 273
   строк): композиция программы с РЕАЛЬНЫМИ байтами lib_c.uva
   оракулом splice (SPEC/10; ключ виртуальной ФС с ../.. —
   оракул не нормализует точки лексически, как и vFS эмулятора)
   → прогон lab_vm.run_asm — консоль/регистры/ловушки ==
   оракулу lab_l4 / якорям BUF (третий свидетель); T-E8-10 —
   ABI-сентинелы r5..r13/r15 вокруг всех четырёх вызовов;
   T-E8-11 — сквозной круг splice.exe → uva.exe (байты .UP ==
   lab_vm.assemble байт-в-байт) → kernel.exe (stdout ==
   оракулу; эмуляция LAB ~0.7 млн шагов — секунды).
   **Батарея 187 → 191/191** (группа 3 — 46/46).
5. **Реестры:** MAP/M4-LIB.md (4 карточки C — «готов», поля
   «Состоит из» дополнены затиранием r1..r4), MAP/METHODS.md
   (статусы C — готов), TESTS/T-L4-LIB.md (T-E8-08..11 +
   статус), MAP/INDEX.md (раздел KERNEL/L4-LIB, счётчики:
   тесты 186, батарея 191), MAP/LAYERS.md, DOCS/02 (строки задач
   L4 + счётчики), DOCS/03-ROADMAP (E8.2 разбит: E8.2a [x],
   E8.2b..d — план), LAB/README, lab_verify.py (докстринг),
   README (статус + сжатие старых абзацев 513 → 476 строк —
   гигиена из очереди мелочей закрыта), JOURNAL (сессия 62).

Дефекты (1 — в собственном тесте, пойман до фиксации):

1. T-E8-10 (ABI): программа не перезагружала r1/r2 после вызова
   lib_buf_out — а r1..r4 ВРЕМЕННЫЕ (ABI): lib_buf_out затирает
   их, lib_buf_out_rev получила r1=5/r2=0 и печатала пусто.
   Дефект ТЕСТА (библиотека верна), пойман локальным прогоном до
   подключения батареи; урок ABI «перезагружай аргументы» —
   записан в тест и CARD.md.

Решения (чтобы не передумывать):

1. **Диффтест на РЕАЛЬНЫХ байтах части** (kfile, не синтетика):
   тест читает KERNEL/L4-LIB/lib_c.uva с диска — проверяется
   именно то, что будет включать программа-потребитель.
2. **Композиция оракулом splice в 08..10, самим splice.exe в 11**:
   сначала дешёвый прогон (мгновенно), затем один дорогой полный
   круг (секунды) — слои проверки как в секциях 14/15 (оракул →
   инструмент).
3. **include ПОСЛЕ halt — конвенция зафиксирована в SPEC/14**
   (уточнение п. 2 без перенумерации) и в CARD.md (рецепт):
   будущие программы-потребители не наступят на грабли «.mem до
   первой инструкции» и «вход на смещении 0».
4. **vFS эмулятора хранит литеральные пути** (не сворачивает
   ../..) — ключ host задаётся полным путём включения; на реальной
   ФС Windows путь разрешается каталогами так же (SPEC/10).

Далее (E8.2b, план сессии 63): ветвь N — lib_n.uva (u64_to_dec_rev:
цикл div/mod 10 + «0»-особый случай; print_u64 = N001 + C004 —
составной вызовами; print_i64 = знак через C001 + 2^64−v) +
диффтесты на якорях DEC/I64/REV (cmp композиция CMP_U64/CMP_I64 —
уже есть свидетели). Затем S (E8.2c), M (E8.2d), E8.3 — демо.

### E8.2b (сессия 63) — ветвь N: числа (первый составной кирпич
### со стеком и первая зависимость ветвей)

План сессии 62 исполнен (ветвь N + диффтесты на якорях DEC/I64/REV).
ЯДРО kernel.exe И ЕГО АРТЕФАКТЫ НЕ МЕНЯЛИСЬ (R7: библиотека —
внешние исходники). Батарея 191 → 196/196 (группа 3 — 51/51).

1. **KERNEL/L4-LIB/lib_n.uva** (новый, 77 строк): 3 кирпича —
   - `lib_u64_to_dec_rev` (K4-N001): цикл div/mod 10 — do-while
     (jnz ВНИЗУ цикла — v = 0 даёт одну итерацию и цифру «0» без
     спец-ветвей); счёт len = p − addr (адрес буфера — в СТЕК-СЛОТЕ
     [sp-8, sp): регистров r1..r4 не хватает на v/p/10/цифру —
     конвенция sp = r13 SPEC/12 п. 3.4 ВПЕРВЫЕ в библиотеке);
     затирает только r1..r4 + слот стека, sp возвращается.
   - `lib_print_u64` (K4-N002): составной ВЫЗОВАМИ (кирпичность:
     сложное из простого) — N001, затем раскладка аргументов
     mov r2, r1 / ldq r1, r13+0 (адрес — сразу из слота в r1) и
     C004 (buf_out_rev печатает старшую слева).
   - `lib_print_i64` (K4-N003): знак — lt с нулём (знаковое «v < 0»
     = v ≥ 2^63); МОДУЛЬ 2^64−v ВЫЧИСЛЯЕТСЯ В r4 ДО печати знака —
     const r1, 45 затирает v (дефект №1 среза, пойман дымовой
     проверкой ДО батареи — см. ниже); «-» через C001 (chr_out
     регистры не трогает — r4 жив); далее N001 + C004 как у N002.
2. **ЗАВИСИМОСТЬ ВЕТВЕЙ N→C зафиксирована** (CARD.md + шапка lib_n.uva):
   N002/N003 вызывают lib_buf_out_rev/lib_chr_out — программа,
   включающая lib_n.uva, обязана включить и lib_c.uva (метки решаются
   в общем плоском тексте — прецедент межчастной композиции).
3. **Диффтесты T-E8-12..16** (`LAB/py/lab_t_l4.py`, 273 → 480 строк):
   - значения шире imm32 — в .data (LE, по 8 Б) + ldq (const умеет
     только знаковый imm32 — SPEC/12 п. 5); циклы печати держат
     курсор/шаг/конец в СОХРАНЯЕМЫХ r5/r6/r7 — выживание цикла
     через вызовы само проверяет ABI;
   - T-E8-12: u64_to_dec_rev — полный контракт карточки: r1 = len И
     RAM-цифры после прогона (якоря REV);
   - T-E8-13/14: print_u64/print_i64 — консоль == оракулу И якорным
     литералам (CMP ⊂ DEC/I64+CRLF — два свидетеля в одном прогоне);
   - T-E8-15: ABI ветви N — сентинелы r5..r12/r15, r14 = memsize И
     sp = r13 СБАЛАНСИРОВАН (r13 == входному — ловит забытый
     pop-слот); RAM-след внутреннего N001 (цифры «01» от −10);
   - T-E8-16: СКВОЗНОЙ КРУГ ИНСТРУМЕНТАМИ с ДВУМЯ частями
     (lib_c + lib_n — первая многокомпонентная композиция):
     splice.exe (две строки !include) → uva.exe (.UP == ассемблеру
     оракула байт-в-байт) → kernel.exe (stdout == оракулу).
4. **Реестры:** MAP/M4-LIB (3 карточки N — «готов», состав/тесты),
   MAP/METHODS (статусы N), TESTS/T-L4-LIB (T-E8-12..16 + статус),
   MAP/INDEX (раздел L4-LIB + счётчики), MAP/LAYERS, DOCS/02 (строки
   L4 + счётчики 196), DOCS/03-ROADMAP (E8.2b [x], сжатие E8.1/2a —
   лимит 500), LAB/README, lab_verify.py (докстринг секции 16),
   README (статус), JOURNAL (сессия 63).

Дефекты (1 — в ветви, пойман до подключения батареи):

1. print_i64: const r1, 45 («-») затирал ЗНАЧЕНИЕ до вычисления модуля
   2^64−v — печать «-(2^64−45)» вместо знаковой записи. Пойман
   дымовой проверкой (scripts вне репо) на якоре I64 (край −2^63);
   фикс — модуль в r4 ДО печати знака (chr_out регистры не трогает).
   Урок: «временная r1..r4 — вычисляй производные ДО её затирания».

Решения (чтобы не передумывать):

1. **Стек-слоты [sp-8,sp) для адреса буфера** (конвенция SPEC/12
   п. 3.4): 4 регистров r1..r4 не хватает (v/p/10/цифра), а r5..r12
   сохраняемые — их использовать МОЖНО только через push/pop —
   тот же стек; карточка и CARD фиксируют требование «программа
   ставит r13 = валидный адрес RAM до вызова ветви N».
2. **len = p − addr, а не счётчик**: длина — производная указателя,
   экономит отдельный регистр; адрес восстанавливается из слота.
3. **Зависимость ветвей = включение ОБЕИХ частей**: у N-программ две
   строки !include (lib_c + lib_n); порядок строк не важен (метки
   глобальны в плоском тексте), важна полнота — иначе ассемблер
   отвергает неразрешённые метки (принцип явности).
4. **64-битные константы в тестах — .data + ldq**, не shl/add-сборка:
   короче, единообразно, заодно покрывает .data/.UP v2 и ldq в
   реальных программах-потребителях.

Далее (E8.2c, план сессии 64): ветвь S — lib_s.uva (str_len/str_out —
циклы до NUL; sp не нужен — можно без стека) + диффтесты на якорях
STR (T-E8-17..21 по схеме N). Затем E8.2d (M: mem_copy/mem_fill —
эффект RAM сверять по r.mem), E8.3 — демо-программы DoD (две).
